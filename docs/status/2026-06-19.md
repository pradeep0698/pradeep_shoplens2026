### Analyze-pipeline performance review (not yet committed)
- Wrote `docs/analyzePerfomanceImprovement.md`: a ranked top-5 list of low-risk performance improvements for the Analyze path (browser → `ai-analyzer` → `product-matcher` → `state-manager`), based on code review since there's no log access to live Cloud Run services from this environment:
  1. Stop blocking the event loop in `product-matcher`/`state-manager` (`await asyncio.to_thread(...)`, matching the pattern `ai-analyzer` already uses) — flagged as a correctness bug, not a tuning choice.
  2. Cut SerpAPI Lens's redundant always-on second call (`visual_matches`) — only fire it when `products` underfills. No latency win (already concurrent), but ~50% fewer SerpAPI calls.
  3. Drop the synchronous per-item GCS delete from the request path — redundant given the bucket's existing 1-day lifecycle rule.
  4. Reuse a `requests.Session()` across SerpAPI calls instead of a fresh session per call.
  5. Downscale images to 1280px max dimension before sending to Gemini (crop boxes are normalized 0–1000 against the original bytes, so this doesn't affect crop quality).
- Started implementing recommendation groundwork in `services/ai-analyzer/analyzer.py` (uncommitted): added a `max_results` parameter to `_search_shopping()` and `_google_lens()` so each detected object pulls exactly 1 listing instead of up to 5, keeping total listings aligned with the user-configured `max_searches` cap — separate from, but related to, the perf-doc recommendations above (#2 in particular still needs to be applied).
