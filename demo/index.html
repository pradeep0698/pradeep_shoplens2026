The Product

What CookShop Does

A live shopping experience embedded into a cooking video stream. AI watches the video and automatically surfaces the products the chef is using — before the viewer even thinks to search.

🎬
Chef goes live
A streamer broadcasts via OBS or any RTMP encoder. No special setup required.
🧠
AI watches in real-time
Every 2-second HLS segment is analysed by Gemini 2.5 Flash, detecting every ingredient and utensil on screen.
🛍️
Shopping list appears
Matched products pop up in the viewer's browser instantly — no page refresh, no manual curation.
⏱️
Target latency: < 5 seconds end-to-end
From the moment a new HLS segment lands in Cloud Storage to the moment the product appears in the browser.

Layer 1

Video Ingestion

RTMP video from any encoder is transcoded to HLS and stored in Cloud Storage — this triggers the entire pipeline.

1
RTMP Input Endpoint
OBS or any encoder pushes a live RTMP stream to the cookshop-input endpoint created by Cloud Live Stream API. The stream key authenticates the connection.
2
HLS Transcoding
cookshop-channel continuously transcodes the RTMP stream and writes HLS segments (2-second chunks) to Cloud Storage. One segment = one AI analysis cycle.
3
Cloud Storage Bucket
All HLS segments land in cookshop-poc-prj-hls-segments. Uniform bucket-level access, no public read — Cloud Run reads via service account.

Layer 2

Event-Driven Pipeline

Cloud Storage notifies Pub/Sub the instant a new HLS segment is written. Pub/Sub pushes it to the orchestrator service.

📣
GCS → Pub/Sub Notification
Every time a new object is written to the bucket, GCS fires an OBJECT_FINALIZE event to the Pub/Sub topic. This is the trigger for the entire AI pipeline.
📨 Pub/Sub Configuration

Subscriptionvideo-segments-sub

The only Cloud Run service exposed to Pub/Sub. It receives the push message, decodes the GCS event, and sequentially calls the three AI/data services.

Layer 3 · Service 1 of 3

AI Analysis — Gemini 2.5 Flash

The ai-analyzer service passes each video segment directly to Gemini and gets back a JSON array of detected items.

🧠
How it works
  1. Receives gs://…/segment.ts from pubsub-worker
  2. Downloads segment bytes from GCS via storage client
  3. Sends video bytes + prompt to Gemini 2.5 Flash (multimodal)
  4. Parses the JSON array response
  5. Returns {"items": ["Tomato", "Chef's Knife", …]}
💬
Prompt strategy
System prompt instructs Gemini to return only a valid JSON array — no markdown, no explanation. Items are concise, capitalised names: "Roma Tomatoes", "Cast Iron Skillet".

Layer 3 · Services 2 & 3 of 3

Product Matching & State

Detected item names are fuzzy-matched to a product catalog, then written to Firestore for real-time browser delivery.

🔍
product-matcher
Uses rapidfuzz WRatio algorithm to fuzzy-match Gemini's item names against a static product catalog. Returns only matches above a 70-point confidence threshold.
Example match:
"roma tomato" → Roma Tomatoes ($2.99)
"cast iron" → Cast Iron Skillet ($39.99)
💾
state-manager → Firestore
Writes matched products to a Firestore document. Each session has a single document that gets overwritten every pipeline cycle — no accumulation logic needed.
Firestore document path:
LiveShoppingSessions / live-session-001
Fields: products[] last_updated
🗄️
Firestore — Native Mode · us-central1
Native mode enables Firestore's real-time listener APIs (onSnapshot). The frontend holds an open WebSocket connection — any document write instantly pushes to all connected browsers with no polling.

Security

Security Model

Zero long-lived credentials. Two service accounts with least-privilege roles. Secrets in Secret Manager, not environment files.

🏃
cookshop-runner
Cloud Run runtime identity — used by all 4 deployed services
datastore.user storage.objectViewer pubsub.subscriber aiplatform.user secretmanager.secretAccessor run.invoker
🔧
cookshop-cicd
CI/CD identity — used only by GitHub Actions via Workload Identity Federation
run.admin artifactregistry.writer iam.serviceAccountUser
🔐
No Service Account Keys
Org policy iam.disableServiceAccountKeyCreation is enforced. No JSON key files anywhere in the repo or CI.
🪪
Workload Identity Federation
GitHub Actions authenticates to GCP using short-lived OIDC tokens. Pool: github-pool, Provider: github-provider.
🔒
Secret Manager
GEMINI_API_KEY and FIREBASE_SERVICE_ACCOUNT_JSON stored as versioned secrets. Cloud Run reads them at runtime via --set-secrets.

What's Next

Remaining Steps to Go Live

Infrastructure is provisioned. Three steps to a working end-to-end demo.

1
Set GitHub Actions Secrets
Add WIF_PROVIDER, WIF_SERVICE_ACCOUNT, Firebase config values, and Gemini API key to the GitHub repository secrets. This unblocks the first deployment.
GitHub → Settings → Secrets
2
Push to main — First Automated Deploy
Pushing to main triggers both workflows. GitHub Actions builds Docker images, deploys all 4 Cloud Run services, updates the Pub/Sub push endpoint automatically, and deploys the frontend to Firebase Hosting.
Fully automated
3
Wire GCS → Pub/Sub Notification
Run one gsutil notification create command to connect the HLS bucket to the Pub/Sub topic. This is the final link that completes the event-driven pipeline.
gsutil notification create -t …/video-segments-topic \
  -f json -e OBJECT_FINALIZE \
  gs://cookshop-poc-prj-hls-segments
🎬
Point OBS at the RTMP endpoint and go live
Stream from OBS → cookshop-channel → HLS to GCS → Pub/Sub → Gemini → product list appears in browser within ~5 seconds. End-to-end demo ready.
