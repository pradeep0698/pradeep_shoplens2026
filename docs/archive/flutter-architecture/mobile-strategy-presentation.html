What It Is

Extend the existing Next.js app with two files. Android Chrome detects them and offers an "Add to Home Screen" prompt. The app launches full-screen with no browser chrome — indistinguishable from a native app to casual users.

1
Add manifest.json — name, icon, display:standalone, theme color
2
Add sw.js — service worker pre-caches app shell for offline & instant load
3
User visits in Chrome → install banner → icon on Android home screen
4
All features work identically — Firebase Auth, Firestore real-time sync, REST APIs, camera via capture="environment"
Best for
MVP validation — prove mobile demand before committing to a native app build
Advantages
✓Ships today — 2–4 hours implementation, no app store approval
✓Zero backend changes — Cloud Run services, Firebase, Firestore all untouched
✓100% code reuse — single codebase serves web and mobile
✓Zero extra infrastructure cost — same Firebase Hosting, no new accounts
✓Auto-updates — no app store release cycle; changes deploy instantly
✓Camera access works — Android Chrome supports native camera capture
✓Offline capable — service worker caches app shell for no-network use
✓One codebase — no parallel maintenance burden on the team
Disadvantages
✗No Play Store listing — zero organic app discovery; can't appear in store search
✗Perceived as a website — tech-savvy users know it's not a "real" app
✗Chrome required — no standalone APK; can't be shared as a file or sideloaded
✗Install prompt not guaranteed — Chrome decides when to show it; criteria can change
✗Web-first UI — no bottom tab bar, no native swipe gestures, no haptic feedback
✗Push notifications unreliable — lower delivery rate vs native FCM on Android
✗Limited device APIs — no NFC, Bluetooth, or background processing
✗Not a ceiling — if Play Store is needed later, we build a native app anyway

What It Is

Capacitor wraps the Next.js static build inside a native Android shell. The web assets are bundled into the APK and loaded in a Chromium WebView. Capacitor plugins provide a JavaScript bridge to native Android APIs.

1
npm run build → Next.js static export → /out/
2
npx cap sync android → copies /out/ into Android project assets
3
Gradle builds APK/AAB — app loads from file://android_asset/ not a remote URL
4
Capacitor plugins extend to native camera, FCM push notifications, filesystem
5
Publish APK/AAB to Google Play Store
Best for
Teams that need a Play Store listing quickly but can't afford any UI rewrite
Advantages
✓100% codebase reuse — zero UI rewrites; existing React/TypeScript unchanged
✓Real Play Store APK — full app store presence and discoverability
✓Native camera plugin — better quality than browser <input capture>
✓Native push notifications — FCM via Capacitor plugin, reliable delivery
✓No new language — team stays entirely in TypeScript and React
✓Extensible — more Capacitor plugins available as app grows
✓Fast to ship — 1–2 weeks to a Play Store listing
✓Live reload in dev — fast iteration cycle during development
Disadvantages
✗WebView rendering — discerning users notice it feels like a browser wrapper
✗Performance limited — WebView is slower than native rendering; animations stutter
✗UI still web-first — no native mobile patterns; mobile UX gap not fixed
✗Play Store review delay — every UI change needs rebuild + re-submission (days)
✗Two deploy pipelines — Firebase Hosting (web) + Google Play (Android) to manage
✗WebView fragmentation — different Android versions have different WebView behavior
✗Larger APK — bundles Chromium overhead compared to a truly native app
✗Worst of both worlds — Play Store complexity without native UX payoff

What It Is

A Turborepo monorepo splits the codebase into a shared /packages/core (API hooks, Firebase logic, TypeScript types) and two platform apps. No WebView — Fabric renderer outputs real native Android components.

1
Shared: useAuth, useShoppingList, useImagePipeline, all API calls, TypeScript types
2
Web UI: existing React + Tailwind unchanged (div, p, img)
3
RN UI: rewritten in View, Text, FlatList — Fabric renderer → real native Android Views
4
Metro bundles the RN app; Gradle builds APK; published to Play Store
Best for
Teams wanting native UX + maximum code reuse from web; iOS later without full rewrite
Advantages
✓Truly native UI — Fabric outputs real Android Views, not HTML in a WebView
✓60–70% code reuse — all API orchestration, Firebase, types shared between platforms
✓Same language — TypeScript + React paradigm; team's existing skills transfer directly
✓iOS path included — same RN codebase targets iOS with minimal extra effort
✓Play Store presence — real APK, full app store listing
✓Native camera + push — react-native-image-picker and FCM messaging
✓Bug fixed once — shared logic bug fixed in core package applies to both platforms
✓Strong ecosystem — Expo, React Navigation, RN Firebase are mature and well-supported
Disadvantages
✗UI must be rewritten — div→View, ul→FlatList; Tailwind CSS does not work in RN
✗Two UI codebases — web components and RN components maintained in parallel
✗Monorepo complexity — Turborepo setup, workspace linking, Metro config adds build overhead
✗React ≠ React Native — subtle behavioral differences trip developers; separate debugging tools
✗4–8 weeks investment — meaningful timeline before anything ships to Play Store
✗RN upgrade pain — major version bumps can introduce breaking changes across the repo
✗Feature parity burden — new features must be built in both web UI and RN UI
✗Metro vs webpack — different bundler, different hot reload, different error messages

What It Is

A completely independent Android app written in Kotlin with Jetpack Compose — Google's modern, recommended native Android stack. MVVM + Hilt DI. Consumes the same REST APIs via Retrofit and the same Firebase project via the native Android SDK.

1
UI: Jetpack Compose screens — LazyColumn shopping list, TextField, Material Design
2
HTTP: Retrofit + OkHttp calling the same /analyze, /match, /session endpoints
3
Firebase: Android SDK — addSnapshotListener mirrors web's onSnapshot
4
Camera: CameraX — full preview, resolution control, HDR; image to Base64 via Android SDK
Best for
When the Android app is a primary product — not a companion to the web app
Advantages
✓Best Android UX possible — indistinguishable from Google or Samsung's own apps
✓Best performance — compiled Kotlin bytecode, no JS or Dart runtime overhead
✓Full Android API access — CameraX, NFC, Bluetooth, background tasks, sensors
✓Clean architecture enforced — Hilt DI, ViewModels, Kotlin Coroutines + Flow by design
✓No runtime abstraction — zero dependency on JS engine, Dart VM, or WebView
✓Best camera access — CameraX with full preview, flash, HDR, and resolution control
✓Zero backend changes — same REST APIs consumed via Retrofit; same Firebase project
✓Future-proof — Jetpack Compose is Google's official, long-term Android UI framework
Disadvantages
✗Zero code sharing — full UI and all business logic rewritten from scratch in Kotlin
✗New language for team — Kotlin is different from TypeScript; React concepts don't map to Compose 1:1
✗Longest timeline — 8–16 weeks minimum for feature parity with the web app
✗Every bug fixed twice — web and Android are independently maintained forever
✗Every feature built twice — new feature on web must be re-implemented in Kotlin
✗Highest maintenance cost — two fully independent apps, two CI/CD pipelines, two signing setups
✗Feature divergence risk — web and app gradually drift apart over time without discipline
✗iOS = another full rewrite — Swift/SwiftUI is a third completely independent codebase

What It Is

Flutter is Google's open-source UI framework using the Dart language. Unlike React Native or Capacitor, Flutter bypasses the native widget system entirely — the Impeller rendering engine draws every pixel directly to the GPU canvas. One codebase ships to Android and iOS.

1
Write UI in Dart using Flutter widgets (Column, ListView, TextField, ElevatedButton)
2
Impeller engine renders directly to GPU — no native widget system involved
3
Camera via image_picker, Firebase via firebase_flutter SDK, REST via dio — same endpoints unchanged
4
flutter build apk → Play Store; flutter build ios → App Store — same Dart code
★ Flutter's unique edge: Android + iOS ship from a single codebase — the strongest cross-platform story of all five options
Advantages
✓Android + iOS in one codebase — best cross-platform ROI; same Dart code targets both stores
✓Own rendering engine (Impeller) — pixel-perfect, consistent UI across all Android device brands
✓Compiled to ARM native code — excellent performance; no JS runtime or WebView overhead
✓Hot reload — fastest dev iteration of all five options; changes appear in under a second
✓Google-backed, long-term — Material Design built-in; strong official support and roadmap
✓Zero backend changes — same REST APIs, same Firebase project; dio calls identical endpoints
✓Dart is learnable — statically typed, similar syntax to TypeScript; JS devs ramp up quickly
✓Consistent UI everywhere — same pixel-perfect look on Samsung, Pixel, OnePlus without tweaking
Disadvantages
✗New language — Dart; TypeScript syntax helps but it's a completely different ecosystem
✗Zero code sharing with web — complete rewrite of all UI and business logic; no shared hooks or types
✗Not native widgets — Flutter draws its own; platform-specific interactions need MethodChannels (verbose)
✗Larger APK size — Flutter Impeller engine adds ~8 MB overhead to every build
✗6–12 weeks investment — Dart learning curve plus full app rewrite; comparable to React Native
✗Every bug fixed twice — Flutter app and web app are fully independent forever
✗Smaller JS ecosystem — fewer third-party packages than npm; some Dart packages less mature
✗Different mental model — Dart widget tree differs from React components; team needs re-orientation

Recommendation & Next Steps

Based on current team size, timeline, and product stage — zero backend changes required for all five options

Our Recommendation — Two-Phase Approach
① PWA now  →  ③ React Native or ⑤ Flutter next

Ship PWA today to validate mobile demand with zero risk. If analytics confirm users want a native app, choose between React Native (if maximising web code reuse matters) or Flutter (if iOS is on the 12-month roadmap and the team is willing to learn Dart).

🚀Phase 1 — today: PWA to prove mobile demand; 2-4 hrs, zero cost
📊Measure: mobile session rate, image-analysis conversion, 7-day retention
🔀Phase 2a — iOS not planned: React Native — reuse 60-70% of web logic in TypeScript
🔀Phase 2b — iOS on roadmap: Flutter — single Dart codebase ships to both stores
🚫Skip Capacitor — WebView UX gap is real; Play Store complexity without native payoff
⏳Native Kotlin — only if Android becomes the primary product, not a web companion
Decision Criteria
Do we need Play Store discoverability right now?
No → PWA  ·  Yes → React Native, Flutter, or Capacitor
Is native UX quality a hard requirement?
No → PWA or Capacitor  ·  Yes → React Native, Flutter, or Kotlin
Do we need iOS within 12 months?
Yes → Flutter (same codebase) or React Native (same codebase)
Does maximising web code reuse matter?
Yes → React Native (60-70% reuse, TypeScript stays)
Is Android the primary product (not web companion)?
Yes + team learns Kotlin → Native Kotlin/Compose
