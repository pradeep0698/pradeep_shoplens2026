# ShopLens Detailed API Specs

Rich OpenAPI 3.0 specs for all 5 backend services, with full request/response
schemas, field-level descriptions, and realistic examples for every status
code — generated by `docs/postman/generate_api_specs_detailed.py`.

## Files

| File | Service |
|---|---|
| `ai-analyzer.openapi.json` | Gemini image/video analysis + product detection |
| `product-matcher.openapi.json` | SerpAPI Google Shopping search/matching |
| `state-manager.openapi.json` | Firestore session state |
| `voice-assistant.openapi.json` | Gemini Live voice preference sessions |
| `pubsub-worker.openapi.json` | Internal Pub/Sub push webhook |
| `index.html` | Swagger UI viewer — dropdown to switch between all 5 specs |

## How this differs from `docs/api-specs/`

`docs/api-specs/*.openapi.json` (generated by `generate_openapi_specs.py`) is
the **raw** FastAPI introspection output — accurate but sparse, because
FastAPI only auto-generates a response schema from a `response_model=`
argument, and none of these services declare one (they return `JSONResponse`
directly). That means the raw spec's response bodies are mostly empty `{}`.

This folder's specs start from that same raw output and add, by hand, from
the real code paths:
- Full response schemas + realistic examples for every documented status code (200/400/401/404/422/500/502 as applicable)
- Named request-body examples covering each real use case (image URL vs base64 vs GCS video URI, etc.)
- A `servers` block (cookshop-dev-rajan-prod, shoplens-dev, local) — the raw spec omits this entirely
- A `firebaseAuth` security scheme on Voice Assistant's 3 protected routes (its auth is checked manually in code, not through FastAPI's Security system, so FastAPI has no way to know about it on its own)

## Viewing it

Open `index.html` in a browser — it embeds Swagger UI with a dropdown to
switch between all 5 services, rendering every endpoint's request body,
response schema/example per status code, and field descriptions.

**Important:** browsers block `fetch()` of local files opened via `file://`
(CORS), so double-clicking `index.html` won't load the specs. Serve the
folder over HTTP first:

```bash
cd docs/postman/apiSpecs
python -m http.server 8000
# then open http://localhost:8000/index.html
```

## Regenerating

```bash
python docs/postman/generate_api_specs_detailed.py                       # all 5 services
python docs/postman/generate_api_specs_detailed.py --service ai-analyzer  # one service only
```

Requires that service's `requirements.txt` deps installed (fastapi,
pydantic, etc.) — not real GCP credentials, since it imports the FastAPI app
directly (see `generate_local()` in `generate_openapi_specs.py`).

**This is not fully hands-off.** Request-side schemas regenerate
automatically from the Pydantic models in code. But response-side schemas,
examples, and status codes are hand-maintained inside
`generate_api_specs_detailed.py`'s `enrich_<service>()` functions — if a
route's response shape changes, a field is added/removed, or a new endpoint
is added, that function needs a matching edit or the detailed spec will
drift from reality. See the `/update-api-specs` skill, which checks for
exactly this before regenerating.
